# Chibimadness — обязательный workflow

## Git-синхронизация

Перед любым изменением обязательно выполнить и оценить:

```powershell
git status --short
git fetch origin --prune
git status -sb
git log --oneline HEAD..origin/main
git log --oneline origin/main..HEAD
```

- Сохраняй чужие изменения: не добавляй их в свой коммит и не удаляй их.
- Если `origin/main` впереди, при чистом дереве используй только `git pull --ff-only origin main`; при грязном — не пытайся автоматически сливать изменения.
- До push повторно fetch-проверь, что remote не изменился.
- Никогда не использовать force-push, `git reset --hard` или удаление файлов для синхронизации без явной команды пользователя.

## Обязательная поставка

После каждого завершённого и проверенного изменения игрового кода, desktop/web-конфига или ассетов не жди отдельной команды:

1. Проверь scope: `git diff --check`, затронутые тесты/сборку и `git status`.
2. Создай небольшой коммит только со своими файлами.
3. Запушь `main` в origin.
4. Сверь remote-теги и создай следующий свободный patch-тег `vX.Y.Z`.
5. Запушь тег и проверь GitHub Actions. В отчёте укажи commit, тег и ссылку/статус workflow.

Не делать тег/релиз для одной диагностики, вопроса или docs-only изменения без явной просьбы.

`publish-release: skipped` у запуска от `main` допустим, когда параллельно идёт tagged workflow. Источником истины является запуск на `vX.Y.Z`, его SHA и созданный release/artifact.

## Server — отдельная поставка

`.github/workflows/release.yml` выпускает client/web-артефакты и **не** деплоит `server/` на VPS.

- При изменении `server/**` после push/tag отдельно сообщай, что требуется server deploy.
- Для Dash применяй только известный проектный `deploy-server.sh`/PM2-процесс после проверки подключения и точного target. Не заявляй, что сервер обновлён, пока deployment не подтверждён.
- Всегда различай «релиз клиента опубликован» и «сервер на VPS обновлён».

## Проверки

- Сначала минимальные проверки затронутой области; не запускать полный workspace без причины.
- Для Rust: один Cargo-процесс, `CARGO_BUILD_JOBS=6`; для тестов также `RUST_TEST_THREADS=6`.
- Если нужные локальные зависимости отсутствуют, не маскируй это: укажи пропущенную проверку и её причину.
